# 1. 目标与范围

## 1.1 版本定义

**v0.1.0（首个可用版本）** 必须交付：

1. `yuxc` CLI：`build / run / test / repl`（repl 可后置）。
2. 覆盖 `01` 语法规范的**核心子集**（§1.2 明确定义包含/排除）。
3. JVM 后端：ASM 直接生成 `.class`（ADR-04）。
4. 编译器插件 SPI：可被 `yux-compiler-minecraft` 加载（02-§10）。
5. `build.yml` → Gradle 构建管线（ADR-12）。
6. `yux.core`/`yux.collection`/`yux.json`/`yux.io`/`yux.async`/`yux.di`/`yux.test` 最小实现。
7. YuxPlugin SDK：`plugin/event/command/config/permission/task` 语法 + 运行时。
8. Home 插件示例（`04`）与混合项目示例（`05`）编译运行通过。

**明确不做（v0.1 范围外）**：

- Native/WASM 后端（只留接口占位，02-§13）。
- `unsafe`/`native fun`/`stack` 的完整语义（只做语法接受 + JVM 降级映射）。
- KMP、Android/iOS 目标。
- 类级增量编译（先文件级）。

# 2. 技术栈与工具链

| 类别 | 选择 | 版本 | 说明 |
| --- | --- | --- | --- |
| JDK | Temurin | 21 | target.jvm=21（ADR-12 配套） |
| 构建 | Gradle | 8.10+ | 编译器自身工程 + 生成脚本 |
| 编译器语言 | Kotlin | 2.0.x | ADR-02 |
| 字节码 | ASM | 9.7 | `asm` + `asm-commons` |
| JSON | Jackson `databind` | 2.17.x | yux.json / 序列化 |
| YAML | SnakeYAML | 2.2 | yux 配置 / SDK config |
| 协程 | kotlinx-coroutines | 1.8.x | async 后端运行时 |
| DI | 自研（轻量） | — | yux.di，避免引入重量框架 |
| 测试 | JUnit 5 + kotlin.test | — | 单测 |
| 快照测试 | 自研 golden 工具 | — | 词法/语法/IR 快照 |

| 命令 YAML 校验 | SnakeYAML | 复用 | build.yml 解析 |

**约定**：

- 编译器自身用 Gradle 8 构建；**产物 `yuxc` 依赖的运行时 jar** 与目标项目区分，目标项目使用 `target.jvm` 指定的 JDK。
- 依赖尽量少：避免引入重型框架（不用 KSP/KAPT）。
- 所有第三方依赖版本集中写在 `gradle/libs.versions.toml`（Version Catalog）。

# 3. 版本与发布策略

- 采用语义化版本 `MAJOR.MINOR.PATCH`：v0.x 阶段 `PATCH` 允许破坏（预发布）。
- 版本节奏：里程碑结束即打 tag（`v0.1.0-m0`、`v0.1.0-m1` …），`v0.1.0` 为 GA 候选。
- 制品：
  1. `yuxc` 发行包（zip/tgz：bin + lib）。
  2. 编译产物发布到 `mavenLocal()`（开发期），后续 Nexus/Artifactory。
  3. `yux-stdlib`、`yux-plugin-minecraft`、`yux-minecraft-runtime` 独立坐标。
- `CHANGELOG.md` 随里程碑更新，记录 breaking changes（预发布阶段需明确说明）。

**设计偏差（相对 02-§8.4）**：

- SSA 版本局部分配独立槽位（不做 coalescing）：φ 拷贝保留为真实赋值，正确性优先；

1. `./gradlew build`（含全部测试）

## 7.3 代码评审约定

- PR 拆分按里程碑粒度；每个 PR 含测试 + 快照 + CHANGELOG 行。
- 编译器核心 PR 需「语法↔语义↔后端」三端对应用例。
- 诊断文本改动走「快照更新 + 审阅」流程。
- 严格 Git Workflow（M5 起强制）见 §7.4。

## 7.4 严格 Git Workflow（M5 起）

> 目标：所有开发统一在单一 feature 分支上进行；`main` 只接受 PR 合入；旧里程碑分支随用随删，避免多分支漂移。

### 分支模型

- 当前唯一开发分支：`feature/m10-mixed-project`；每个里程碑只允许一个 `feature/<milestone>` 分支。
- `main` 是受保护集成分支：禁止直接开发/提交/push，只通过 GitHub PR 合入。
- 不再创建或保留 `m<里程碑>-<主题>` 临时分支；已合入 feature 的内容直接删除本地与远端旧分支。

### 提交规范

- 提交信息以 `T-<里程碑>-<任务>` 开头（如 `T-M5-1: ...`），或使用 `fix:`/`docs:` 等 conventional commit 风格。
- 每个提交/PR 必须可构建且测试通过；测试、golden 快照、CHANGELOG 随变更一起落地。
- 禁止对共享 feature 分支 force push；需要改写历史时先确认。

### PR 与评审

- PR 按里程碑粒度拆分，目标一律为 `main`。
- 必须通过 CI（`./gradlew build lint` + 覆盖率门禁）与 CodeRabbit/人工评审。
- 诊断文本或 golden 快照变更必须同步更新快照，并在 PR 中说明。
- 合并后的旧分支立即删除（本地 + 远端）。

### 验收命令

```
git branch -a
# 期望：本地仅当前 feature 分支；远端仅 origin/feature/<里程碑>、origin/main 与 origin/HEAD
```
